# tools/core-to-core-latency/ —— 核间通信延迟

测一台机器上任意两个核之间传递一个缓存行要多久。这个数决定了所有**争用型**并发原语的扩展上限：自旋锁、原子计数器、SPSC 队列、以及内核的 IPI / 广播 TLBI。

主要用途是跨机型对比。本仓库的 B1 基准在 arm64 上扩展性变差，根因追到广播 TLBI 的序列化；核间延迟就是那件事的底层量纲。

## 目录内容

| 文件 | 说明 |
| --- | --- |
| `c2c.c` | 自己实现的 ping-pong 测量，约 100 行 C，只依赖 pthread |
| `run.sh` | 驱动：编译、跑、收集；可选一并跑 Rust 的 `core-to-core-latency` |
| `analyze.py` | 汇总：分布、分块热图、方法间一致性、跨机器对比。只用标准库 |

## 用法

```bash
# 测本机
bash run.sh

# 测远端若干台（会 scp c2c.c 过去就地编译）
SSH_KEY=~/key.pem bash run.sh 10.0.0.1 10.0.0.2

# 同时跑 Rust 工具（没装会自动 cargo install）
SSH_KEY=~/key.pem WITH_RUST=1 bash run.sh 10.0.0.1 10.0.0.2

# 分析
python3 analyze.py ./c2c-20261015-052240
```

环境变量：`ITERS`(4000)、`REPS`(3)、`WARMUP`(2000)、`WITH_RUST`(0)、`RUST_ITERS`(1000)、`RUST_SAMPLES`(100)、`SSH_USER`(ubuntu)、`SSH_KEY`、`OUTDIR`。

96 核跑满 4560 对，`c2c.c` 约 20 秒；带 Rust 工具两个 bench 约 3–7 分钟。

输出目录里每台机器一组：`<label>.meta.txt`（机型、拓扑、loadavg）、`<label>.siblings.txt`（SMT 映射）、`<label>.c2c.csv`（`a,b,one_way_ns`）、`<label>.tool-b{1,2}.{csv,txt}`。

## 原理

### 为什么用 ping-pong

两个线程分别 pin 到核 A 和 B，共享一个 `atomic_int`：

```
A: store(1)  →  自旋等 flag==2
B: 自旋等 flag==1  →  store(2)
```

一次往返恰好是这条缓存行的**两次所有权转移**（A→B，B→A），没有别的内存流量。被测的就是 cache coherence 协议把一行从一个核的 L1 搬到另一个核的 L1 所需的时间。

`c2c.c` 里那行 `_Alignas(4096)` 不是随手写的：要保证这条行不和任何其他数据 false sharing，4 KiB 对齐在 64 B（这两种 CPU）和 128 B（部分 arm64）行长下都安全。

### 为什么报往返除以二

往返 = 两次转移，所以 `one_way = RTT / 2`。这是业界通用口径（Rust 的 `core-to-core-latency` 也这样报），好处是能直接和厂商公布的 fabric 延迟比。

但它**不是纯硬件单向线延迟** —— 里面含 store-release、load-acquire 和自旋检测的开销。同一套方法测不同机器，比值可信；拿它和论文里的硬件参数硬比，不可信。

### 为什么取多轮最小值

每对核测 `REPS` 轮、每轮 `ITERS` 次往返，取**最小**的那一轮。中断、抢占、迁移只会让样本更慢，永远不会更快，所以下界是对硬件路径最干净的估计。用均值会把偶发的调度噪声混进去。

### 三种方法分别压什么

| 方法 | 原语 | 缓存行数 |
| --- | --- | --- |
| `c2c.c` | plain store / load（release / acquire） | 1，双向共用 |
| 工具 bench 1 | **CAS**（compare-and-swap，read-modify-write） | 1，双向共用 |
| 工具 bench 2 | 单写单读 | **2，每个方向一条** |

这三个不是同一个量，不能混着引用。bench 1 的 CAS 需要独占所有权且是 RMW，比 plain store 重；bench 2 用两条行，避免了同一行上的读写所有权冲突，更像真实的 SPSC 环形队列。

## 解析：实测结果

两台 96 逻辑核的 AWS metal，空闲状态（loadavg < 0.2）：

| | m7i.metal-24xl | m8g.metal-24xl |
| --- | --- | --- |
| CPU | Xeon Platinum 8488C (Sapphire Rapids) | Neoverse-V2 (Graviton4) |
| 拓扑 | 48 核 × 2 线程，1 socket | 96 核 × 1 线程，1 socket |
| L3 | 105 MiB | 36 MiB |
| NUMA | 1 | 1 |

单向延迟中位数，ns，**只统计不同物理核的对**：

| 方法 | m7i (x86) | m8g (Graviton4) | 比值 |
| --- | --- | --- | --- |
| `c2c.c` 单行 store/load | **57.6** | **105.8** | arm 慢 1.84x |
| bench 1 CAS 单行 | **58.2** | **103.7** | arm 慢 1.78x |
| bench 2 双行 SPSC | **143.0** | **111.0** | **arm 快 1.29x** |

完整分布：

```

m7i  c2c.c   跨物理核   med  57.6   p25 52.0  p75 63.4  (38.8 – 94.9)
m7i  bench1  SMT 同核   med   5.8
m7i  bench1  跨物理核   med  58.2   p25 52.4  p75 64.1  (38.3 – 86.3)
m7i  bench2  SMT 同核   med  18.9

m8g  bench2             med 111.0   p25 105.1 p75 118.0 (89.5 – 136.0)
```

### 为什么排名会反转

这是这份测量最重要的结论，也是只跑一种方法会得出错误结论的地方。

从单行换到双行：

- x86：57.6 → 143.0 ns，**涨 2.5 倍**
- arm：105.8 → 111.0 ns，**几乎不动（1.05 倍）**

Graviton4 的代价几乎完全由 fabric 穿越决定，对访问模式不敏感。Sapphire Rapids 对「一条持续保持热的行」有很强的优化 —— 行一直在少数核附近，所有权交接走的是短路径；但换成两条各自要冷取的行时，每次都要完整的 snoop + 远端取回，优势就没了。

**这部分机制是推断，没有用 PMU 计数器验证。** 稳妥的说法只有现象本身：单行争用 x86 快约 1.8 倍，双行 SPSC arm 快约 1.29 倍。

实践含义：

- 受**单条争用行**支配的负载（自旋锁、原子计数器、`mmap_lock` 这类、广播 TLBI / IPI）—— x86 占优约 1.8 倍。本仓库 B1 在 arm64 上的扩展性问题属于这一类
- 受**双行交接**支配的负载（写得好的 SPSC 队列、io_uring 式环形缓冲、DPDK 风格收发队列）—— Graviton4 占优约 1.29 倍

所以「arm 核间通信更慢」这句话只在前一类成立。

### 拓扑结构

两台都是单 NUMA 节点，而且**都没有 chiplet 台阶** —— 延迟连续分布，没有「组内快、跨组突然慢一截」的断层。

m8g（`c2c.c`，12 核一块，块内中位数）是一个平滑的碗：

## 注意事项

### 1. 不要解读单个核对

`analyze.py` 会打出方法之间的逐对相关性，实测：

```
m7i   bench1 vs c2c.c    r = +0.405   差值中位数 +0.8 ns
m8g   bench1 vs c2c.c    r = -0.024   差值中位数 -2.9 ns
m8g   bench2 vs c2c.c    r = +0.711   差值中位数 +6.0 ns
```

注意 m8g 上 bench1 和 `c2c.c` 的 **r 只有 -0.024**，等于完全不相关 —— 但两者的分布中位数只差 2 ns，分块热图的形状也一致。

也就是说：**分布和分块结构是可复现的，具体哪一对核更快不可复现。** 可能的原因是 `c2c.c` 固定让编号小的核当发起方，而工具的方向处理不同，若 fabric 存在方向不对称就会系统性分歧；也可能只是单对的测量噪声（差值 p95 在 14–22 ns）。没有定论。

结论只能建到分布、分位数和块级结构上。想比较两个具体核，必须专门多轮重测那一对。

### 2. SMT 必须单独拆出来

x86 上同物理核的两个超线程共享 L1，`c2c.c` 测出 17.2 ns、bench 1 只有 5.8 ns —— 这根本不过 fabric，和跨核的数不是一个量。混在一起算均值会把结论带偏。

`run.sh` 会把 `/sys/.../topology/thread_siblings_list` 存进 `<label>.siblings.txt`，`analyze.py` **从文件读映射**而不是假设 `i` 与 `i+48` 配对（这台机器恰好是这个规律，别的机型不一定）。

### 3. `cargo install` 必须加 `--locked`

distro 的 cargo 是 1.75，直接装会因为依赖解析挑到要求 rustc ≥ 1.88 的 `textwrap` 而失败：

```
package `textwrap v0.16.4` cannot be built because it requires rustc 1.88 or newer
```

加 `--locked` 走 crate 发布时锁定的版本集即可（`run.sh` 里已经这么做）：

```bash
cargo install --locked core-to-core-latency
```

### 4. 机器必须空闲

取最小值能抵掉偶发噪声，但抵不掉持续负载。`run.sh` 会把 loadavg 记进 `meta.txt`，读结果前先确认它接近 0。上面那组数据是在 loadavg 0.03 / 0.18、零沙箱的状态下测的。

### 5. 跨机器比较要同方法同参数

`ITERS` / `REPS` 太小会让结果系统性**偏低**：`ITERS=500 REPS=2` 时 m7i 中位数是 55.1 ns，`ITERS=4000 REPS=3` 是 57.6 ns。

原因在估计量本身 —— 每轮次数少则每轮均值的方差大，而我们取的是多轮**最小值**，分布越宽下界就越低。所以小参数不是「更快」，是估计偏差。对比不同机器时必须用同一套参数，默认值就是为此定的。
